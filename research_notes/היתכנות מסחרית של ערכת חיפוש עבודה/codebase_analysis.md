# Job Search Kit codebase: what it does today and what it would take to productize it

Scope: internal-source analysis of the public repo `nadavfisch/job-search-kit` at commit `72f22dd` (HEAD = origin/main, checked 2026-10-06). All file links point to `https://github.com/nadavfisch/job-search-kit/blob/main/<path>`. Nothing under `my-search/` (private user data) was read. "G/" below abbreviates `https://github.com/nadavfisch/job-search-kit/blob/main/`.

## 1. What is the end-to-end user flow, and which steps are deterministic Python vs. LLM judgment in the agent?

### Takeaway
The kit is an "agent-native" app: there is no UI and no LLM call in the code. The product logic is split between (a) ~1,830 lines of plain, deterministic Python CLI scripts (fetching, validation, rendering, bookkeeping) and (b) ~835 lines of Markdown instructions (AGENTS.md, SETUP.md, workflows/*.md) that a coding agent (Claude Code or Codex) reads and executes. Every judgment step (parsing the CV into facts, triage, tailoring, reviewing, cover letters, form filling, outreach, inbox classification, interview prep) is done by the agent following prose; the scripts act as guardrails and tools around it.

### Cited Findings
- The product is positioned as "A job search run by your AI coding agent (Claude Code or Codex)… Everything runs on your machine, and your data stays in one git-ignored folder." Install requires Claude Code or Codex, Python 3.9+, Google Chrome and git. — [README.md](https://github.com/nadavfisch/job-search-kit/blob/main/README.md)
- No LLM SDK or API is called anywhere in `kit/`: a grep for `anthropic|openai|api_key` in `kit/*.py` returns nothing; the only network calls are `urllib` requests to job boards/LinkedIn in `sources.get()`. — [kit/sources.py](https://github.com/nadavfisch/job-search-kit/blob/main/kit/sources.py)
- AGENTS.md is the agent's "map": a task table routes requests to workflow files (setup → SETUP.md; find jobs → workflows/search.md; inbox → workflows/inbox.md; tailor → workflows/tailor.md; review → workflows/review.md; submit → workflows/apply.md; cover letter; outreach; interview; status → `kit/stats.py` then "summarize in plain words"). — [AGENTS.md](https://github.com/nadavfisch/job-search-kit/blob/main/AGENTS.md)
- Claude Code integration is 10 one-paragraph skills (`/job-setup`, `/job-search`, `/job-tailor`, `/job-review`, `/job-apply`, `/job-cover-letter`, `/job-outreach`, `/job-inbox`, `/job-status`, `/job-interview`), each just "Follow `workflows/<x>.md`. Read `AGENTS.md` first". — [.claude/skills/job-tailor/SKILL.md](https://github.com/nadavfisch/job-search-kit/blob/main/.claude/skills/job-tailor/SKILL.md), [.claude/skills/job-review/SKILL.md](https://github.com/nadavfisch/job-search-kit/blob/main/.claude/skills/job-review/SKILL.md)
- Two "rules that matter most" are behavioral instructions to the agent: (1) never invent experience; (2) write every decision to a file immediately because "A new session sees only files, never this conversation" (facts → profile.yaml, preferences → preferences.md "Decisions", form answers → answers-bank.md ✅, per-job → tracker.md, events → log.md via `kit/log.py`, people → contacts.md). — [AGENTS.md](https://github.com/nadavfisch/job-search-kit/blob/main/AGENTS.md)

Step-by-step (D = deterministic script, L = LLM/agent judgment, B = browser agent, H = human approval):
- **Setup (~15 min)**: D `kit/render.py --check` (Chrome present), D `kit/extract_text.py` (PDF/DOCX/text → text); L build `profile.yaml` from the CV ("every achievement, each under a short key… don't add facts"), L ask clarifying questions ("numbers without context… Never fill a gap with a guess"); L/H 10-question interview on roles, location, salary, deal-breakers, banned phrases, approval policy, referrals, CV language/RTL, target companies, email/calendar tools; D `kit/build.py master` + D `kit/preview.py`; optional look-matching: D `kit/pdf_style.py` + L writes CSS variables + L compares output to original ("at most 3 builds"); L writes `search.yaml` with D `kit/sources.py guess/detect`; L writes permission allowlist to `.claude/settings.local.json`. — [SETUP.md](https://github.com/nadavfisch/job-search-kit/blob/main/SETUP.md)
- **Search**: D `kit/search.py` + D `kit/fetch_jd.py <date> new`; L triage every new job with a description: "Fit 1-10", decision `apply|stretch|referral|skip`, "Why: one sentence"; L writes `batches/<date>/triage.md`; H user approves; D `kit/new_job.py --batch <date> --id <id>` opens a job folder + tracker row. — [workflows/search.md](https://github.com/nadavfisch/job-search-kit/blob/main/workflows/search.md)
- **Tailor**: L reads JD (top 5 requirements, exact keywords, requirement→bullet mapping or "gap"), L writes `spec.yaml`; D `kit/build.py --check <n>` then D `kit/build.py <n>`; L reacts to "DOESN'T FIT" / "page only N% full". — [workflows/tailor.md](https://github.com/nadavfisch/job-search-kit/blob/main/workflows/tailor.md)
- **Review**: L, a separate clean-context reviewer ("a writer checking its own work is a weak check") writes `review.md` with verdict ✅/⚠️/❌ against a 19-item rubric (truth, fit, ATS/standards, cover letter). — [workflows/review.md](https://github.com/nadavfisch/job-search-kit/blob/main/workflows/review.md), [workflows/parallel.md](https://github.com/nadavfisch/job-search-kit/blob/main/workflows/parallel.md)
- **Apply**: D `kit/check_ready.py`, D `kit/preview.py`, H approval per `preferences.md`, D `kit/pace.py` before each LinkedIn submission, B fill/upload/submit, L edits tracker row, D `kit/log.py submitted`. — [workflows/apply.md](https://github.com/nadavfisch/job-search-kit/blob/main/workflows/apply.md)
- **Cover letter** (only when a form asks): L writes 250-350 words; D `kit/letter.py <n> --check` and render. — [workflows/cover-letter.md](https://github.com/nadavfisch/job-search-kit/blob/main/workflows/cover-letter.md)
- **Outreach/follow-up**: B find ≤3 people per job on LinkedIn/company site; L draft notes (LinkedIn 200-char limit, "Count characters in code"); H user sends every message; D `kit/log.py message-sent`; follow-ups due listed by D `kit/stats.py`. — [workflows/outreach.md](https://github.com/nadavfisch/job-search-kit/blob/main/workflows/outreach.md)
- **Inbox** (optional email connector): L classify job-alert emails into leads (D `kit/add_lead.py`) and company replies into rejection/interview/assessment/reply/auto-ack, update tracker, D `kit/log.py`; optional calendar events. — [workflows/inbox.md](https://github.com/nadavfisch/job-search-kit/blob/main/workflows/inbox.md)
- **Interview**: L writes `interview-prep.md` (top 5 requirements, gaps, likely questions, company research, 3 questions to ask) and a shared `interview-bank.md` of locked answers and 6-8 STAR stories; missing details marked "[fill in]". — [workflows/interview.md](https://github.com/nadavfisch/job-search-kit/blob/main/workflows/interview.md)
- **Stats**: D `kit/stats.py` prints pipeline counts, submitted/responded/interview rates overall and per source, "Waiting to submit", "Follow-ups due", "No answer for 3+ weeks", last-7-days events; L summarizes. — [kit/stats.py](https://github.com/nadavfisch/job-search-kit/blob/main/kit/stats.py)

### Inferences
- The deterministic layer is small and well-factored, but it is the "skeleton"; the value a user perceives (good triage, good tailoring, honest review, form filling) lives in the prompts plus the frontier model. A product must re-implement the agent loop as orchestrated LLM calls with structured outputs.
- The workflows already follow a "LLM proposes → code verifies → LLM repairs" pattern (spec.yaml → build.py --check → fix), which maps cleanly onto a server-side pipeline with retries.
- Human-in-the-loop checkpoints are explicit and frequent (fact confirmation, triage approval, CV preview, submission approval, open questions batched at the end, user sends all messages): this is a ready-made UX spec for an approval-centric product.

### Gaps
- No telemetry or real usage data exists in the repo, so how long each step takes in practice, or how often the agent violates the prose rules, cannot be measured from the code.

## 2. What job data sources are supported, and how (APIs vs. scraping)?

### Takeaway
Three automated source types in `kit/search.py`: LinkedIn (HTML scraping of logged-out "guest" endpoints), six ATS job boards via their public JSON APIs (Greenhouse, Lever, Ashby, Workable, SmartRecruiters, Comeet; Comeet needs a token scraped from its HTML page), and one remote board (Remotive API). Workday, iCIMS, Taleo, Indeed, Glassdoor etc. are not search sources; they enter only via email alerts or manual leads (`kit/add_lead.py`), and a "custom careers site" is checked by the agent in a browser.

### Cited Findings
- `search.py` sources = `("linkedin", "companies", "remote")`; results merge into `batches/<batch>/jobs_all.json`; jobs whose id appeared in any earlier batch get `"new": false`. Default look-back `days: 14`. — [kit/search.py](https://github.com/nadavfisch/job-search-kit/blob/main/kit/search.py), [templates/search.yaml](https://github.com/nadavfisch/job-search-kit/blob/main/templates/search.yaml)
- **LinkedIn search**: GETs `https://www.linkedin.com/jobs-guest/jobs/api/seeMoreJobPostings/search?keywords=…&location=…&f_TPR=r<days*86400>&start=<0|25|50>[&geoId=…]`, parses HTML cards with regexes (`jobPosting:(\d+)`, `base-search-card__title`, `base-search-card__subtitle`, `job-search-card__location`, `datetime=`), sleeps 1.2 s between pages, stops paging when a page returns <20 cards, and prints "nothing came back (maybe rate-limited)" on zero results. Up to 3 pages × 25 per query; `search.yaml` asks for 10-30 queries. LinkedIn results are added without the `title_keywords/title_exclude/locations` filter (`wanted()` is applied only to company and remote sources). — [kit/search.py](https://github.com/nadavfisch/job-search-kit/blob/main/kit/search.py), [SETUP.md](https://github.com/nadavfisch/job-search-kit/blob/main/SETUP.md)
- **LinkedIn descriptions**: `fetch_jd.py` GETs `https://www.linkedin.com/jobs-guest/jobs/api/jobPosting/<id>` per job, regex-extracts `show-more-less-html__markup`, job criteria and the applicant count, sleeps 1.5 s per job (3 s after an error), and prints "EMPTY (closed, or blocked: don't triage an empty description)". — [kit/fetch_jd.py](https://github.com/nadavfisch/job-search-kit/blob/main/kit/fetch_jd.py)
- All HTTP uses `urllib` with a spoofed desktop Chrome User-Agent string (`Mozilla/5.0 (Macintosh… Chrome/128.0…`), 30 s timeout, manual 307/308 redirect following. — [kit/sources.py](https://github.com/nadavfisch/job-search-kit/blob/main/kit/sources.py)
- **ATS endpoints** (all normalized to `{id, title, company, location, date, url, source, description}`):
  - Greenhouse: `https://boards-api.greenhouse.io/v1/boards/{slug}/jobs?content=true` (id `gh-<slug>-<id>`)
  - Lever: `https://api.lever.co/v0/postings/{slug}?mode=json` or `api.eu.lever.co` when `eu: true`
  - Ashby: `https://api.ashbyhq.com/posting-api/job-board/{slug}` (skips `isListed: false`)
  - Workable: `https://apply.workable.com/api/v1/widget/accounts/{slug}?details=true`
  - SmartRecruiters: `https://api.smartrecruiters.com/v1/companies/{slug}/postings?limit=100&offset=…` (pages up to 1,000); the per-job detail call is a lazy callable "fetched later, only if the job passes the filters"
  - Comeet: needs the company's Comeet page URL; scrapes a `"token"` from that HTML, then calls `https://www.comeet.co/careers-api/2.0/company/{uid}/positions?token=…&details=true`
  - Remotive: `https://remotive.com/api/remote-jobs?search=<q>&limit=50`, filtered by `remote.allowed_locations` and `title_exclude` — [kit/sources.py](https://github.com/nadavfisch/job-search-kit/blob/main/kit/sources.py)
- Company-board filter `wanted()`: whole-word title keyword match ("AI" matches "AI Lead", not "Retail"), exclusion words, substring location match, and a posting-date cutoff. — [kit/search.py](https://github.com/nadavfisch/job-search-kit/blob/main/kit/search.py)
- Board discovery: `sources.py guess "<company>"` tries 3 slug variants of the name on Greenhouse, Lever, Ashby, Workable only; `sources.py detect <careers url>` regex-scans the careers page HTML for Greenhouse/Lever/Ashby/Workable/SmartRecruiters/Comeet links; otherwise "the agent checks this company in the browser instead". — [kit/sources.py](https://github.com/nadavfisch/job-search-kit/blob/main/kit/sources.py), [workflows/search.md](https://github.com/nadavfisch/job-search-kit/blob/main/workflows/search.md)
- The template calls the company-board route "official public APIs, no scraping", and the README calls it "official and stable". — [templates/search.yaml](https://github.com/nadavfisch/job-search-kit/blob/main/templates/search.yaml), [README.md](https://github.com/nadavfisch/job-search-kit/blob/main/README.md)
- Email alerts (AllJobs, Drushim, Indeed, Glassdoor, Wellfound, LinkedIn Job Alerts) are read through an email connector by the agent, which opens each link to get the full description and adds it with `kit/add_lead.py` (id = `lead-` + first 10 hex chars of the SHA-1 of the link). — [workflows/inbox.md](https://github.com/nadavfisch/job-search-kit/blob/main/workflows/inbox.md), [kit/add_lead.py](https://github.com/nadavfisch/job-search-kit/blob/main/kit/add_lead.py)
- Workday appears only as a form type the browser agent may meet when applying ("Greenhouse, Lever, Comeet, Workday..."), not as a search source. — [workflows/apply.md](https://github.com/nadavfisch/job-search-kit/blob/main/workflows/apply.md)
- Israel-first signals: Comeet support, AllJobs/Drushim, a LinkedIn `geo_id` example for Israel ("101620260"), Tel Aviv examples, Hebrew RTL CVs. — [templates/search.yaml](https://github.com/nadavfisch/job-search-kit/blob/main/templates/search.yaml), [SETUP.md](https://github.com/nadavfisch/job-search-kit/blob/main/SETUP.md), [README.md](https://github.com/nadavfisch/job-search-kit/blob/main/README.md)
- Dedup: across batches by job id (`seen`); at job-folder creation `new_job.py` refuses a link already in the tracker; "same company + title" dedup is an LLM instruction in triage. — [kit/search.py](https://github.com/nadavfisch/job-search-kit/blob/main/kit/search.py), [kit/new_job.py](https://github.com/nadavfisch/job-search-kit/blob/main/kit/new_job.py), [workflows/search.md](https://github.com/nadavfisch/job-search-kit/blob/main/workflows/search.md)

### Inferences
- The ATS fetchers (Greenhouse/Lever/Ashby/Workable/SmartRecruiters) are the most product-ready asset: public, unauthenticated JSON endpoints, a normalized schema, offline-tested parsers. In a SaaS they could become a shared crawler: one fetch of a company board serves every user tracking that company.
- Coverage is the main gap for a product: no Workday, iCIMS, Taleo/Oracle, SuccessFactors, Recruitee, Teamtailor, Personio, BambooHR, JazzHR, or aggregators (Indeed/Glassdoor/Google Jobs), so large-enterprise jobs come only through LinkedIn or email alerts. Users must also list target companies by hand.
- LinkedIn is the only "discovery" source (search by keyword rather than a fixed company list), and it is the legally and technically fragile one (scraping guest HTML with regexes, a spoofed UA, explicit ToS conflict). For a hosted product, running it from data-center IPs for many users would hit rate limits and blocks much harder than one person's home IP does (the code already expects rate limiting).
- Because LinkedIn results skip the keyword/location prefilter, every LinkedIn hit goes to LLM triage. That drives up token cost per batch (see Q6).

### Gaps
- No measurement in the repo of how many jobs a typical search returns per source, or how often LinkedIn rate-limits.
- Whether Comeet's token-in-page approach and Workable's widget endpoint are officially supported public APIs could not be verified from the code (the code treats them as public).

## 3. How is truthfulness enforced, precisely?

### Takeaway
Truthfulness is a layered mechanism: (1) an approved fact base, `profile.yaml`, that only grows after the user confirms; (2) a constrained CV spec format where bullets are references to profile keys or keyed rewordings; (3) a deterministic validator (`build.py` `problems()`) that refuses to render on unknown keys, misplaced or duplicate bullets, overlapping bullets, any number not in the profile (with number normalization), a reworded bullet that adds a number its own source lacks, user-defined banned regexes, and title-level inflation; (4) a pre-submit gate (`check_ready.py`) that re-runs the checks and ties PDF ↔ spec ↔ fresh review; and (5) an independent LLM reviewer for meaning-level claims the code can't catch. This is the kit's clearest differentiator, and it is also partial: free text (summary, title, custom skills lines, rewordings) is only checked for numbers and banned patterns.

### Cited Findings
- `profile.yaml` is "Your approved facts. Every CV is built only from what's in this file… A new fact… gets in only after you approve it." Schema: `name, headline, contact, links, summary, experience[{key, header, bullets{key: text}, default[]}], education[], skills{key:{label,text}}, languages, max_pages, rtl, labels, separator, rules{overlaps, banned[{pattern, why}], title_banned}`. — [templates/profile.yaml](https://github.com/nadavfisch/job-search-kit/blob/main/templates/profile.yaml)
- A tailored `spec.yaml` holds `title`, `summary`, `experience[{role, bullets: [<key> | {from: <key>, text: "<reworded>"}]}]`, `skills: [<key> | {label, text}]`, `education: bool`. — [workflows/tailor.md](https://github.com/nadavfisch/job-search-kit/blob/main/workflows/tailor.md), [examples/demo/jobs/001 - Globex - Operations Automation Lead/spec.yaml](https://github.com/nadavfisch/job-search-kit/blob/main/examples/demo/jobs/001%20-%20Globex%20-%20Operations%20Automation%20Lead/spec.yaml)
- `problems(p, raw)` errors on: no title; an experience entry that isn't a dict; unknown role key; a role listed twice; a string bullet that isn't a profile key ("Free text must be {from: <key>, text: ...}"); a rewording with an unknown source key; a rewording that "adds numbers its source doesn't have" (checked against **that source bullet's** numbers only); a bullet under the wrong role; a bullet used twice; more than one bullet from a `rules.overlaps` group; an unknown skills key or a malformed skills entry; in every text (title, summary, each bullet, each skills line) any number "not in profile.yaml" (the global set of numbers from headline, summary, languages, education, role headers, all bullets and skills texts); any `rules.banned` regex match (case-insensitive) with the user's own `why` message; and `rules.title_banned` matching the title ("title inflates level"). — [kit/build.py#L76-L158](https://github.com/nadavfisch/job-search-kit/blob/main/kit/build.py#L76-L158), [kit/build.py#L56-L61](https://github.com/nadavfisch/job-search-kit/blob/main/kit/build.py#L56-L61)
- Number normalization: regex `NUMBER` plus `SCALE` treat "2,000", "2K" and "2 thousand" as the same value (Decimal with a scale for k/thousand/m/mm/mn/million/b/bn/billion); "10x" and "200ms" count as 10 and 200; digits inside names like "B2B", "Web3", "v2.0" and the phrase "0-to-1" are skipped. — [kit/build.py#L29-L53](https://github.com/nadavfisch/job-search-kit/blob/main/kit/build.py#L29-L53), tested in [tests/test_checks.py](https://github.com/nadavfisch/job-search-kit/blob/main/tests/test_checks.py) (incl. "a number glued to Hebrew still counts")
- Structure enforcement: experience is always re-sorted to profile order (reverse-chronological) whatever order the spec uses; "Tailor through the title, summary, and bullet choice, never through order." — [kit/build.py#L122-L123](https://github.com/nadavfisch/job-search-kit/blob/main/kit/build.py#L122-L123)
- All-or-nothing: "Nothing renders if any spec fails a check" (`sys.exit("Spec errors, nothing rendered…")`). AGENTS.md forbids loosening checks: "Fix the spec; never loosen the check or edit profile.yaml just to make it pass." — [kit/build.py](https://github.com/nadavfisch/job-search-kit/blob/main/kit/build.py), [AGENTS.md](https://github.com/nadavfisch/job-search-kit/blob/main/AGENTS.md)
- Cover letters get the same number check against the whole profile, the banned patterns, and a 400-word cap. — [kit/letter.py](https://github.com/nadavfisch/job-search-kit/blob/main/kit/letter.py)
- Pre-submit gate `check_ready.py`: re-runs `problems()`; requires the PDF for the *current* spec title; page count ≤ `max_pages`; the PDF's extracted text (whitespace-stripped) must contain the summary and every bullet, so a stale PDF is caught (skipped for RTL); `review.md` must exist, be newer than the PDF, and its first verdict sign must not be ❌. "Not checked: whether the posting is still open." — [kit/check_ready.py](https://github.com/nadavfisch/job-search-kit/blob/main/kit/check_ready.py)
- Immutability: once the tracker's "Submitted" date is filled, `build.py` and `letter.py` skip that job unless `--force` ("A submitted PDF is never overwritten"). — [kit/build.py#L161-L167](https://github.com/nadavfisch/job-search-kit/blob/main/kit/build.py#L161-L167), [kit/letter.py](https://github.com/nadavfisch/job-search-kit/blob/main/kit/letter.py), [AGENTS.md](https://github.com/nadavfisch/job-search-kit/blob/main/AGENTS.md)
- What code can't catch is delegated to the reviewer: "Already enforced by kit/build.py: invented numbers, unknown bullets, duplicates, the user's banned phrases. The reviewer checks meaning, which code can't." Truth items: every claim backed by profile.yaml; "no upgraded verbs (helped → led, tracked → defined), no wider scope"; no unheld level in the title; nothing contradicting preferences. Any truth failure = ❌. — [workflows/review.md](https://github.com/nadavfisch/job-search-kit/blob/main/workflows/review.md)
- Tailoring rule: "No new number, tool or scope; build.py rejects a number the source bullet doesn't have, and you must not add claims it can't catch (scope, ownership, seniority)". A custom skills line "may reorder or drop items, never add one that isn't in the profile" (prose rule). — [workflows/tailor.md](https://github.com/nadavfisch/job-search-kit/blob/main/workflows/tailor.md)
- Form answers: only ✅-approved answers from `answers-bank.md`; "A form question with no ✅ answer: don't make one up. Leave that form unsent… ask all the open questions together at the end." "Never guess salary, years, or yes/no eligibility questions." — [AGENTS.md](https://github.com/nadavfisch/job-search-kit/blob/main/AGENTS.md), [workflows/apply.md](https://github.com/nadavfisch/job-search-kit/blob/main/workflows/apply.md), [templates/answers-bank.md](https://github.com/nadavfisch/job-search-kit/blob/main/templates/answers-bank.md)
- Interview prep: "No new facts here either… Where a real detail is missing, write [fill in]." — [workflows/interview.md](https://github.com/nadavfisch/job-search-kit/blob/main/workflows/interview.md)

### Inferences
- Machine-enforced: provenance of every bullet (a key into an approved library), numeric integrity, role/bullet placement, duplicate/overlap control, user-specific banned phrases and title inflation, PDF-matches-spec, review freshness. Not machine-enforced: new tools, skills, scope or seniority words in the free-text summary, title, rewordings and custom skills lines (custom skills lines are not checked against the profile's tool list at all). Those depend on the LLM reviewer and on prompt compliance.
- For a product this is a strong, explainable trust feature ("we can show which approved fact every line came from, and we block invented numbers"). It could be strengthened cheaply, for example with a tool/skill-vocabulary check for custom skills lines and summaries, or an NLI/entailment check of each rewording against its source bullet.
- The design pattern (a structured fact library + keyed references + a validator + an independent reviewer) is portable to a database model (facts table, CV version referencing fact ids, a validation service).

### Gaps
- No evaluation data on false positives/negatives of the number check, or on how often the LLM reviewer catches upgraded verbs or scope inflation in practice.

## 4. How are PDFs rendered, what are the dependencies, and what is the data model?

### Takeaway
CVs and letters are HTML strings built in Python and printed to PDF by spawning a local headless Chrome/Chromium/Edge process. A fit-to-page binary search over 17 typographic steps (11 pt → 9.4 pt) can launch Chrome up to about 6 times per CV. Runtime deps are minimal (`pypdf`, `pyyaml`, a Chromium-family browser, network access to Google Fonts). All state is local files: YAML (profile, specs, search config), Markdown tables parsed by regex (tracker, log, contacts, answers), JSON (batches), and plain-text job descriptions, in one git-ignored folder.

### Cited Findings
- `render.py`: writes a temp `.html`, runs `chrome --headless=new --disable-gpu --no-pdf-header-footer --virtual-time-budget=8000 --print-to-pdf=<out> <file>` with a 120 s timeout, then counts pages with `pypdf`. The browser is found via `CHROME_PATH` or known macOS/Windows paths or `google-chrome|chromium|microsoft-edge` on PATH. — [kit/render.py#L19-L40](https://github.com/nadavfisch/job-search-kit/blob/main/kit/render.py#L19-L40), [kit/render.py#L135-L162](https://github.com/nadavfisch/job-search-kit/blob/main/kit/render.py#L135-L162)
- Fit algorithm: `STEPS` = 17 tuples interpolated from roomy `(11.0pt, line-height 1.45, top 14mm, section 13pt, job 8.5pt)` to tight `(9.4, 1.3, 8, 6, 4)`; `render()` binary-searches the roomiest step that fits `max_pages` (default 1), then renders once more and measures `page_fill` (lowest text line ÷ page height). Returns `"OVERFLOW"` if even the tightest step doesn't fit. Binary search over 17 steps is at most 5 probes plus 1 final render, so ≤6 Chrome launches per CV. — [kit/render.py#L165-L195](https://github.com/nadavfisch/job-search-kit/blob/main/kit/render.py#L165-L195)
- `build.py` warns "page only N% full" when a 1-page CV is <75% full, renders to `.rendering.pdf` and atomically replaces, and deletes older PDFs rendered under a different title. — [kit/build.py#L210-L235](https://github.com/nadavfisch/job-search-kit/blob/main/kit/build.py#L210-L235)
- Page size is fixed A4 (`@page { size: A4 }`, `.page { width: 210mm }`), and the letter is also A4. There is no US Letter option. — [kit/render.py#L49-L75](https://github.com/nadavfisch/job-search-kit/blob/main/kit/render.py#L49-L75), [kit/letter.py](https://github.com/nadavfisch/job-search-kit/blob/main/kit/letter.py)
- Fonts are loaded at render time from `https://fonts.googleapis.com/css2?family=Questrial&family=Roboto…`. — [kit/render.py#L128](https://github.com/nadavfisch/job-search-kit/blob/main/kit/render.py#L128)

### Inferences
- The HTML/CSS template, the fit-to-page search, the page-fill check and the ATS CSS guard are reusable as-is in a rendering microservice. But "spawn a fresh Chrome per probe, ≤6 per CV, fonts fetched from Google each time" is fine on a laptop and wasteful at scale. A product would keep a warm browser pool (e.g. Playwright/Puppeteer page reuse) or a dedicated HTML-to-PDF service, self-host fonts, and add US Letter for North America.
- The file model is effectively a schema already (well-defined columns, enums, keys). It maps one-to-one onto relational tables: profiles/facts, skills, rules, preferences/decisions, answers, search configs, postings, batches, applications (tracker), events (log), contacts, documents (object storage). Markdown tables parsed by `split("|")`, and concurrency handled by prose rules, are the parts that don't survive multi-user hosting.

### Gaps
- Render latency per CV was not measured (Chrome isn't installed in this environment; the 7 Chrome tests were skipped).

## 5. How does submission work (browser agent, pace limits)?

### Takeaway
Submission is done by a general-purpose browser agent (Claude in Chrome, or the Codex Chrome extension) driving the user's own logged-in Chrome, guided by a prose checklist and hard-won DOM hacks. Gates are a deterministic readiness check, an approval policy that is a prose rule rather than a technical lock, and a LinkedIn pacing script that counts log lines. Without a browser agent, the kit falls back to "prepare everything, user submits", which is the most portable mode for a product.

### Cited Findings
- "Submitting and finding contacts need a browser agent signed in to the user's accounts: Claude in Chrome (Claude Code), or the Codex Chrome extension (Codex app)." A per-site permission prompt can't be turned off. "Without one, prepare everything (PDF path, link, every form answer) and the user submits by hand." — [AGENTS.md](https://github.com/nadavfisch/job-search-kit/blob/main/AGENTS.md)
- Per-job procedure: `check_ready.py`; order newest/fewest applicants first; approval per preferences.md (default: show list + open CVs with `preview.py`, wait for OK); `pace.py` before each LinkedIn submission; open the posting and confirm it's open and not already applied; identify the method (Easy Apply or company site); fill from ✅ answers + profile; upload the job's PDF; no-✅ question → close the form unsent and add it to the open questions; consent/privacy/terms boxes only with explicit OK per box; untick "Follow <company>"/newsletters; submit within policy and confirm; tracker row `submitted`, Submitted = today, Follow-up = +7 days; `kit/log.py submitted --details "<how>"`. — [workflows/apply.md](https://github.com/nadavfisch/job-search-kit/blob/main/workflows/apply.md)
- "Browser tips (learned the hard way)": click by accessibility-tree element reference, not coordinates; set long text through the native value setter in JS plus an `input` event, because "typing drops characters"; for LinkedIn Easy Apply file upload, temporarily override `HTMLInputElement.prototype.click` so the file input attaches instead of opening the OS picker; LinkedIn number fields take integers; open embedded iframe forms (e.g. Comeet) at their own URL; "Company-site uploads are often blocked for agents. Don't work around it: fill everything else and leave the upload and submit to the user." The round report covers CAPTCHAs, logins and manual uploads. — [workflows/apply.md](https://github.com/nadavfisch/job-search-kit/blob/main/workflows/apply.md)
- `pace.py`: counts today's `submitted` rows in `log.md` whose details match `linkedin|easy apply`; defaults 15/day, 5/hour, 3-minute gap (CLI flags); exit 1 with WAIT or "STOP for today". It does not read preferences.md: changed limits apply only if the agent passes the flags. — [kit/pace.py](https://github.com/nadavfisch/job-search-kit/blob/main/kit/pace.py), [templates/preferences.md](https://github.com/nadavfisch/job-search-kit/blob/main/templates/preferences.md)
- Outreach pacing is prose only: "open only the profiles you'll actually list (at most 3 per job, about 20 a day)". The agent never sends messages or clicks Send. — [workflows/outreach.md](https://github.com/nadavfisch/job-search-kit/blob/main/workflows/outreach.md)
- The approval gate is not technical in the "almost none" permission mode: "You still stop before submitting (the approval policy in preferences.md), but that's your own rule, not a technical gate." — [SETUP.md](https://github.com/nadavfisch/job-search-kit/blob/main/SETUP.md)
- Risk framing to users: "LinkedIn's User Agreement forbids automated access… applying runs in your own logged-in browser, so it is [tied to your account]… The worst likely outcome is a temporary restriction with an identity check, but the risk to your account is yours." — [README.md](https://github.com/nadavfisch/job-search-kit/blob/main/README.md)
- Parallelism: the browser "should have one owner: two sessions clicking in the same Chrome trip over each other"; applying is called "the real bottleneck". — [workflows/parallel.md](https://github.com/nadavfisch/job-search-kit/blob/main/workflows/parallel.md)

### Inferences
- The submission layer is the least productizable part. It depends on a third-party agentic browser running locally with the user's sessions, it is slow (one form at a time, a 3-minute LinkedIn gap), it breaks on CAPTCHAs and upload blocks, and pacing depends on the LLM logging correctly (pace.py trusts the log text).
- Product options, in rising order of risk: (a) an "apply pack" (link + PDF + copy-ready answers), which the kit already defines; (b) a client-side browser extension that autofills ATS forms in the user's own session with explicit click-to-submit; (c) server-side headless submission, which would require holding users' credentials or cookies, conflicts with LinkedIn's UA, and would face CAPTCHAs. ATS-hosted forms (Greenhouse/Lever/Ashby) are the most automatable targets; LinkedIn Easy Apply is the riskiest.

### Gaps
- No data on submission success rates, time per application, or how often a site blocks the agent.

## 6. Rough LLM work per tailored application and per search batch

### Takeaway
Because every judgment step runs in the agent, LLM work per application is about 4-6 model "steps" for prep (triage share, tailor, 0-2 repair loops, independent review, optional fix/re-review, optional cover letter) plus a browser-driven submission. A lean, orchestrated product implementation would need about 10-35k input and 1-4k output tokens per tailored application before submission. Run as today's agent sessions with subagents and browser automation, the same work consumes an order of magnitude or two more (hundreds of thousands to low millions of input tokens, largely cache reads), with the browser submission dominating. These are estimates; the assumptions are listed below.

### Cited Findings
- Instruction sizes an agent reads (bytes, measured with `wc -c`): AGENTS.md 9,514; SETUP.md 10,147; workflows/tailor.md 2,942; review.md 2,789; search.md 3,439; apply.md 4,279; cover-letter.md 1,981; outreach.md 2,909; interview.md 1,997; inbox.md 2,713; parallel.md 3,156. The demo profile.yaml (2 roles, 7 bullets) is 2,586 B; the demo JD is 640 B. — [AGENTS.md](https://github.com/nadavfisch/job-search-kit/blob/main/AGENTS.md), [workflows/](https://github.com/nadavfisch/job-search-kit/tree/main/workflows), [examples/demo/profile.yaml](https://github.com/nadavfisch/job-search-kit/blob/main/examples/demo/profile.yaml)
- LLM steps defined per job: triage (fit score, decision, one-line reason, per job; a big batch is split into subagents of 20-30 descriptions each), tailor (read JD → spec.yaml → build-check loop), review by a *new* subagent (inputs: PDF text, JD, spec.yaml, cover letter if any, profile.yaml, preferences.md; output review.md with findings and "exact suggested rewording"), cover letter only when a form asks for one ("Not by default"), and apply via the browser. — [workflows/search.md](https://github.com/nadavfisch/job-search-kit/blob/main/workflows/search.md), [workflows/parallel.md](https://github.com/nadavfisch/job-search-kit/blob/main/workflows/parallel.md), [workflows/tailor.md](https://github.com/nadavfisch/job-search-kit/blob/main/workflows/tailor.md), [workflows/review.md](https://github.com/nadavfisch/job-search-kit/blob/main/workflows/review.md), [workflows/cover-letter.md](https://github.com/nadavfisch/job-search-kit/blob/main/workflows/cover-letter.md)
- Per-batch volume drivers: LinkedIn uses 10-30 queries × up to 3 pages × 25 cards in a 14-day window; LinkedIn results are not keyword-filtered before triage; company boards are filtered by keywords/locations/date first. Collection itself (search.py, fetch_jd.py) uses no LLM tokens. — [SETUP.md](https://github.com/nadavfisch/job-search-kit/blob/main/SETUP.md), [kit/search.py](https://github.com/nadavfisch/job-search-kit/blob/main/kit/search.py)

### Inferences
Assumptions (not from the repo): ~4 characters per token for English; a real JD is 3-6k chars (~0.75-1.5k tokens; the 640 B demo JD is unrepresentative); a real profile.yaml is 6-12 KB (~1.5-3k tokens: 4-6 roles, 25-40 bullets including short variants); preferences.md ~0.3-0.75k tokens; CV text ~0.6-0.9k tokens; spec.yaml output ~0.4-0.8k tokens.

**A. Lean orchestrated pipeline (direct API calls, only the needed inputs):**
| Step | Calls | Input tokens | Output tokens |
|---|---|---|---|
| Triage (batched 20-30 JDs per call, shared profile/prefs/rubric amortized) | ~1/25 per job | ~0.9-1.7k per job | ~60-100 per job |
| Tailor (rubric ~0.75k + profile + prefs + JD) | 1 | ~3.3-6k | ~0.4-0.8k |
| Repair loops (build errors, DOESN'T FIT, thin page) | 0-2 | 0-13k | 0-1.6k |
| Independent review (rubric ~0.7k + CV text + spec + JD + profile + prefs) | 1 | ~4.3-7.7k | ~0.4-1k |
| Fix + re-review after ⚠️/❌ (assume ~1 in 3 jobs) | 0-2 | 0-14k | 0-1.8k |
| Cover letter (only when requested) | 0-1 | ~3.5-6.5k | ~0.5k |
| Form-answer mapping from answers-bank (non-browser "apply pack") | 0-1 | ~1-3k | ~0.2-0.5k |
- Typical prep (triage + tailor + review): **~9-16k input / ~1-2k output tokens per application**. Heavy case (repairs + re-review + letter + answers): **~25-45k input / ~3-5k output**. That is ~5-8 LLM calls per application.
- Per search batch (triage only): with 50-150 new jobs with descriptions, ~50-250k input and ~3-15k output tokens. Setup (CV → profile, interview, master CV, search.yaml) is a one-time conversation, plausibly ~50-150k input tokens across turns.

**B. As run today (agent sessions):** each agent turn re-sends the accumulated context (system prompt + tool schemas + AGENTS.md + every tool result so far). Assuming a 20-35k-token context and 6-12 tool turns, a tailoring subagent processes roughly 150-400k input tokens (mostly prompt-cache reads) and a review subagent 100-300k. Browser submission is the dominant cost: 15-40 browser tool calls per application, with page text/accessibility trees of several thousand tokens each and screenshots, plausibly 0.5-3M cumulative input tokens per application (heavily cached). Outreach (people search + ≤3 profile views + drafts) adds a similar browser-heavy load. These numbers are order-of-magnitude only.
- Implication: a product that replaces the free-form agent loop with targeted structured calls can cut prep tokens by 10× or more, and replacing agentic browsing with a deterministic autofill extension removes the largest token sink entirely.

### Gaps
- No real profiles/JDs/session logs were examined (my-search/ is off-limits and no telemetry exists), so all token figures are modeled, not measured. Claude Code/Codex system-prompt and tool-schema sizes are not documented in the repo. Converting tokens to dollars needs current model pricing, which is out of scope for this subtopic.

## 7. Which parts are reusable in a product, and which depend on the AI coding agent / browser agent?

### Takeaway
Reusable with modest refactoring: the job-source connectors, the truth validator, the CV renderer with its ATS guardrails, the readiness gate, the CV text/style extraction, the stats funnel, the pacing logic, and the workflow Markdown as ready-written prompt specs and rubrics. Agent-dependent: all judgment steps, file editing of the tracker/contacts/preferences, subagent orchestration, permission handling, email/calendar via MCP connectors, and all browser work (apply, outreach, custom careers sites, fetching alert-email links).

### Cited Findings

- Several scripts are top-level CLI code (argparse at import time, `print`, `sys.exit`), not importable functions: `search.py`, `fetch_jd.py`, `check_ready.py`, `pace.py`, `letter.py`, `stats.py`, `log.py`, `new_job.py`, `add_lead.py`, `pdf_style.py`, `preview.py`. Tests drive them as subprocesses ("running a kit script like the agent does"). — [kit/search.py](https://github.com/nadavfisch/job-search-kit/blob/main/kit/search.py), [kit/check_ready.py](https://github.com/nadavfisch/job-search-kit/blob/main/kit/check_ready.py), [tests/helpers.py](https://github.com/nadavfisch/job-search-kit/blob/main/tests/helpers.py)

- Email/calendar are optional connectors (e.g. Gmail, Google Calendar), read-only by rule ("never send, delete or archive mail unless the user asks"). — [AGENTS.md](https://github.com/nadavfisch/job-search-kit/blob/main/AGENTS.md), [workflows/inbox.md](https://github.com/nadavfisch/job-search-kit/blob/main/workflows/inbox.md)
- Language behavior is an agent instruction: talk in the user's language; CVs and form answers in the posting's language; English choice dialogs for RTL users. — [AGENTS.md](https://github.com/nadavfisch/job-search-kit/blob/main/AGENTS.md)
- The process is user-editable: "everything the agent does is plain Markdown in AGENTS.md and workflows/. Edit it like any document." — [README.md](https://github.com/nadavfisch/job-search-kit/blob/main/README.md)

### Inferences
- The workflow files are a high-quality prompt library: the triage rubric, tailoring rules, a 19-point review rubric, the cover-letter structure and banned clichés, outreach-note rules, and the interview-prep template. They can be lifted almost verbatim into system prompts for discrete, structured-output LLM calls.
- The "everything is a file the next session reads" principle is an agent workaround for missing memory. In a product it becomes ordinary database persistence, plus an audit log of decisions and approved facts. Its spirit is worth keeping: every user decision is recorded and reused, and questions get asked once.
- Today's distribution model (clone a GitHub repo into a coding agent, approve Python and browser permissions) limits the audience to technical users. That is the main reason a consumer product would need a full rebuild of the interaction layer, even though the core logic is reusable.

### Gaps
- Codex-specific behavior (beyond "browser extension works in the Codex app, not the CLI") is not documented in the repo.

## 8. What would break or need rebuilding for a multi-user hosted product?

### Takeaway
Almost everything around the core logic changes: local files → a multi-tenant database and object storage; an agent following Markdown → an orchestrated LLM pipeline with structured outputs and a job queue; local Chrome rendering → a scalable PDF service; the user's logged-in browser agent → an extension or an "apply pack"; LinkedIn guest scraping from one home IP → a server-side legal and technical liability; "your data never leaves your machine" → a real privacy/security program for highly sensitive PII and possibly mailbox access.

### Cited Findings
- Current privacy promise: "Everything about you lives in my-search/, which git ignores… Nothing is uploaded anywhere except what you submit to employers, and what your AI agent's provider processes during the conversation". `.gitignore` comment: "Your personal data never leaves your machine". — [README.md](https://github.com/nadavfisch/job-search-kit/blob/main/README.md), [.gitignore](https://github.com/nadavfisch/job-search-kit/blob/main/.gitignore)
- Sensitive data held: contact details, salary expectations, work authorization/visa, EEO/diversity answers, notice period, people contacted, interview notes, and (with connectors) email contents and calendar. — [templates/answers-bank.md](https://github.com/nadavfisch/job-search-kit/blob/main/templates/answers-bank.md), [templates/contacts.md](https://github.com/nadavfisch/job-search-kit/blob/main/templates/contacts.md), [workflows/inbox.md](https://github.com/nadavfisch/job-search-kit/blob/main/workflows/inbox.md)
- First run already contemplates cloud sessions with data in a separate private git repo cloned into `my-search/` ("every change to it is committed and pushed back to that repo"). — [AGENTS.md](https://github.com/nadavfisch/job-search-kit/blob/main/AGENTS.md)
- Single-user assumptions in code: workspace = one folder (`my-search/` or `JOBKIT_WORKSPACE`); job numbers = max folder number + 1; tracker edits are regex/Markdown based; `preview.py` opens a local PDF viewer (`open`/`xdg-open`/`os.startfile`); timestamps use local `datetime.now()`. — [kit/common.py](https://github.com/nadavfisch/job-search-kit/blob/main/kit/common.py), [kit/new_job.py](https://github.com/nadavfisch/job-search-kit/blob/main/kit/new_job.py), [kit/preview.py](https://github.com/nadavfisch/job-search-kit/blob/main/kit/preview.py), [kit/log.py](https://github.com/nadavfisch/job-search-kit/blob/main/kit/log.py)
- LinkedIn scraping relies on logged-out guest endpoints and a spoofed UA, and already expects rate limiting ("If nothing comes back, LinkedIn is rate-limiting: wait, don't retry in a loop"). — [kit/search.py](https://github.com/nadavfisch/job-search-kit/blob/main/kit/search.py), [workflows/search.md](https://github.com/nadavfisch/job-search-kit/blob/main/workflows/search.md)
- Rendering spawns a local Chrome process per probe (≤6 per CV), 120 s timeout, fonts from Google at render time. — [kit/render.py](https://github.com/nadavfisch/job-search-kit/blob/main/kit/render.py)

### Inferences
Proposed productized architecture (the kit's own boundaries, re-hosted):
1. **Data layer**: Postgres (users, profiles, facts/bullets with provenance and approval timestamps, skills, rules, preferences + decision log, answers with approval state, search configs, postings, batches, applications, events, contacts, documents), object storage for CVs/letters, per-tenant encryption of sensitive fields, retention/deletion tooling (GDPR-style data-subject requests).
2. **Ingestion service**: port `sources.py` to scheduled workers with a shared posting cache keyed by ATS + slug (cost scales with companies, not users); add connectors (Workday, Recruitee, Teamtailor, Personio, SmartRecruiters already present…) or licensed job feeds; drop or isolate server-side LinkedIn scraping (or move it to a client-side extension running in the user's own browser, mirroring today's "from the user's machine" posture).
3. **LLM orchestration**: a queue of discrete calls (CV→facts extraction with a user-confirmation UI, triage, tailor→`problems()` validation→repair, independent reviewer with a different prompt and ideally a different model, cover letter, interview prep, inbox classification), with structured JSON outputs instead of free-form agent tool use, prompt caching of profile/rubrics, and per-user cost metering.
4. **Rendering service**: a warm headless-Chromium pool or HTML-to-PDF service, self-hosted fonts, A4 + US Letter, the existing fit/ATS checks.
5. **Submission**: an "apply pack" UI by default; an optional browser extension for ATS autofill with user click-to-submit; pacing enforced in code, not prose; no server-side use of user LinkedIn sessions.
6. **Email/calendar**: OAuth integrations (read-only scopes) for alerts and replies. Google's restricted-scope verification for Gmail read access is likely required (needs verification, not covered here).
7. **Trust UX**: show each CV line's source fact; block unapproved numbers, tools and titles; require explicit approval for new facts and for each submission (today partly honor-system).
- What survives unchanged: the truth model, the validator, the template and ATS rules, the source parsers, the rubrics, and the funnel metrics in `stats.py` (submitted → responded → interview → offer by source).
